# Code quality review

Reviewed 3 October 2026. The review covered the application TypeScript/TSX under
`app/`, `components/`, `lib/`, `scripts/`, and `types/`, with particular attention
to correctness risks, code smells, and long functions. Generated dependencies
under `node_modules/` were excluded.

## Findings

### High — Prototype persistence is enabled in every non-test runtime

`persistEnabled()` returns true in development and production, so application
requests ultimately use a process-local `Map` plus a synchronous JSON file. The
read-modify-write sequence has no lock or atomic rename, and each process has an
independent in-memory snapshot. Concurrent requests or multiple application
instances can overwrite one another; serverless/ephemeral deployments can also
lose the file entirely. Synchronous filesystem calls additionally block the
request worker. The name `prototypePersistence` signals the intended scope, but
the runtime guard does not enforce it.

**Recommendation:** make the prototype backend an explicit opt-in development
adapter and fail closed in production. Use the existing database-backed stores
for deployed environments. If file storage remains useful locally, serialize
writes and write to a temporary file followed by an atomic rename.

### High — Submission ordering compares display strings rather than timestamps

`listPrototypeSubmissions()` sorts `submitted_at` with `localeCompare`, while the
stored value is a human-formatted string such as `27 Aug 2026, 3:14 pm`. Lexical
order is not chronological across days, months, or years, so the submissions UI
can silently show an incorrect “newest first” order.

**Recommendation:** store an ISO-8601 timestamp (or epoch) as the canonical value,
sort numerically, and format only at the presentation boundary. Add a regression
test spanning different months and years.

### Medium — Users & Access networking can leave the UI stale or reject unhandled

`load()`, `openManage()`, `provision()`, and `commit()` assume both `fetch()` and
`response.json()` succeed. Network failures, aborted requests, and non-JSON 5xx
responses therefore escape the event handler without a user-facing error.
`openManage()` also has no request identity or cancellation: opening user B before
user A's slower response returns can replace the drawer with user A. The repeated
`setBusy(false)` in `commit()` is a small but concrete sign that this flow is hard
to maintain.

**Recommendation:** extract a typed request helper that normalizes transport,
HTTP, and decoding errors; cancel or sequence detail requests; and split the
mutation-to-request mapping and success-message mapping into exhaustive helpers.

### Medium — Access-directory listing performs an N+1 fan-out

For every identity, `toView()` independently loads staff and customer membership
and may then load a property name. `list()` runs these concurrently, but still
issues up to `3N` datastore calls. `listImplementationOptions()` independently
adds another property lookup per implementation. This will increase latency and
can exhaust connection or rate limits as the directory grows.

**Recommendation:** add bulk store methods (or a joined database query) that load
identities, access records, and implementation names in bounded queries. Assemble
views from maps in the service layer and cover the query count in a store/service
test.

### Medium — A clean checkout cannot run the advertised typecheck directly

The `typecheck` script runs only `tsc --noEmit`, but `app/layout.tsx` relies on the
global `LayoutProps` generated by Next.js. With `.next` ignored, `npm run
typecheck` fails before Next has generated route types. This makes local and CI
results depend on whether another Next command happened to run first.

**Recommendation:** run `next typegen` before `tsc --noEmit` in the typecheck
script, as required by the installed Next.js documentation, and exercise that
script from a clean workspace in CI.

### Low — Silent catches hide corruption and storage failures

The persistence loader treats every read or JSON parsing exception as “first
run,” then may seed and overwrite the store. A permissions error, truncated file,
or malformed record is therefore indistinguishable from a missing file. Similar
intentional catches in browser storage are acceptable fallbacks, but the server
store should not suppress operational failures.

**Recommendation:** handle only the missing-file error as first run. Log and
surface other failures, validate the parsed schema, and quarantine rather than
overwrite malformed data.

## Long-function and cohesion hotspots

| Hotspot | Approximate size | Why it is difficult to change | Suggested seam |
| --- | ---: | --- | --- |
| `UsersAccessScreen` | 520 lines (lines 207–726) | Owns request orchestration, filters, drawer state, confirmation state, access rules, and most page markup. | `useAccessDirectory` reducer/hook; `AccessSummary`, `AccessFilters`, `AccessRows`, and an accessible drawer component. |
| `ManageBody` | 195 lines (lines 840–1034) | Several account-type/role transitions and audit rendering are interleaved in one render tree. | Account-specific action panels and a standalone audit list. |
| `createAccessDirectoryService` / `manage` | 240 / 137 lines | Authorization, last-admin policy, transition dispatch, auditing, and view hydration share one closure. | Exhaustive action handlers plus reusable policy checks; keep each database transition atomic. |
| `ConnectSetupScreen` | 520-line file | Many PMS-specific workflows and conditional render paths live together. | Route-strategy components keyed by connection mode, with shared field primitives. |
| `selectors.ts` | 501-line module | Validation, navigation, display formatting, payload mapping, and masking have accumulated in one utility module. | `validation`, `navigation`, `display`, and `serialization` modules with focused tests. |

The largest files are not automatically defects. The first refactoring priority
should be `UsersAccessScreen`: the race/error issue already crosses its UI and
network responsibilities. The access service should be refactored only alongside
transaction-level tests so that security invariants are not weakened.

## Positive observations

- Domain ports and in-memory/Supabase adapters are generally separated, making
  service testing practical.
- Access inputs use discriminated unions, which is a strong base for exhaustive
  action handling.
- The suite has broad behavioral coverage (243 of 246 tests passed in this
  environment); the three failures require Supabase public configuration.
- ESLint passes without suppression comments in application source.

## Checks performed

- `npm run lint` — passed.
- `npm run typecheck` — failed because generated `LayoutProps` is unavailable in
  a clean checkout.
- `npm test` — 243 passed and 3 failed; the failures are the Supabase connectivity
  checks and report missing public environment configuration.
- Source line-count and targeted smell scans were used to identify hotspots;
  findings were then verified against the relevant implementations rather than
  inferred from file size alone.
